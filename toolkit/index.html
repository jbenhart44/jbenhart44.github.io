Spec-Driven Development, in Practice

Spec-Driven Development treats planning, building and checking as three separate jobs, not one long conversation with a model. You write down what you intend before you build it. You build against that written intent. Then something other than the agent that built it checks the result against the intent.

This did not start as an SDD project. It started as a toolkit for PhD research, where one invented citation or misquoted number can sink a dissertation. The hard rules and verification commands came out of mistakes of that kind. The SDD name came later, when GitHub's SpecKit, Obra's Superpowers and the agents.md convention arrived at the same split.

/pcv shows the pattern in one command. It asks clarifying questions one at a time, writes the plan down, has a critic agent attack it, and waits for your approval before anything is built. The other commands use the same discipline.

The toolkit holds its own releases to the same standard. A script checks the command count and version on every page against the installer. Each check has been made to fail: a copy with a planted defect must turn its own test red. CI runs every check on Linux and macOS on each push.

A collection of 24 Claude Code commands that catch errors, prevent bad plans, and keep complex projects on track. Organized into five layers: setup, verification, workflow, content, and triage. Run /setup once and the commands use your folders and workstreams, not anyone else’s.

Performance Gaps the Toolkit Fills

AI coding assistants do a lot, but they bring no structure of their own. Three gaps come up again and again:

Verification Gap

How do you know the AI’s output is correct, above all for citations, numbers and analysis?

Planning Gap

Complex multi-component projects need structured planning, not ad-hoc prompting.

Documentation Gap

Progress disappears when the terminal closes, because a session’s context does not carry over. Summaries and startup briefs give the AI a record for each workstream to load when the next session starts, so it does not rebuild the state from scratch.

The toolkit adds that structure with reusable commands. Each one was built for a real research task, used on real work, then generalized for others.

Use the Tools in a Chatbot

No Claude Code? Some of these tools also work as a prompt in an ordinary chat. Open a tool, copy its prompt into a new chat, and give it your material when it asks. Each prompt is the tool’s own instructions with the Claude Code file header and markers removed. A short preface tells the chatbot what it cannot do in a chat (run commands, open your files, start separate agents) and that it must never claim to have done them.

Written with Claude, usable with any assistant. These tools were written for Claude Code and tested with Claude models. Each chat prompt opens with a short preface that tells the assistant what it cannot do in a chat and to ignore the parts about installing and configuration files. A few lines still name Claude Code or a Claude account; if the assistant asks which Claude account you use, say you are not using Claude Code. You can paste the prompts into ChatGPT, Gemini, Copilot or whichever assistant you use. Their results there have not been measured: check what comes back the way each prompt tells you to.

A long prompt can be more than a chatbot accepts in one message. The /coa, /pace and /quarto prompts are the longest, about 54,000 to 65,000 characters; the others are under 20,000. If a chat will not take one, open it as text, save it, and attach the file instead of pasting it.

Download all 12 chat prompts (ZIP) with a README that says what each one is for.

Which Model Each Agent Requests

This section is about Claude Code. A chatbot uses whichever model you picked there.

Nine tools start agents: /coa, /pace, /review, /daily-summary, /weekly-summary, /readable, /acquire, /meeting-breakdown, and /quick-ten when it convenes a council. Each one names the model it requests on the call itself, rather than inheriting your session’s model. The model comes from one table, chosen by the account you give /setup. A test fails the build if any command leaves its model unnamed. /pcv also starts agents, with the models its own files name; the same test checks those names against a recorded list.

AgentsSmaller plans
Pro, Team Standard, not sure		Larger plans
Max, Team Premium, Enterprise, API, cloud provider
Council seats (also in a /quick-ten council), cross-check and rebuttal; PACE players, coaches and reviewers; review lenses; /meeting-breakdown players and coachesSonnetSonnet
The /coa Chair, whose synthesis is the one you readSonnetOpus, if /model lists it
The daily and weekly summary writersSonnetSonnet (never Haiku)
The page transcriber of /readable and /acquire, for a scanned PDFHaiku, two readers that must agree on every numberSonnet

Smaller plans: Pro, a Team Standard seat, or “not sure”. Larger plans: Max 5x, Max 20x, a Team Premium seat, Enterprise, the API, or a cloud provider. Smaller plans also get a three-seat /coa council and a two-agent /meeting-breakdown by default; ask for the full run when you want it.

A cost policy, not a claim about your account. Anthropic’s guidance is to use Sonnet for teammates (Claude Code costs), and says Opus “costs several times more per turn than Sonnet” (Models, usage, and limits in Claude Code). So only the Chair moves to Opus, and only on accounts with a larger allowance. Haiku reads scanned pages on smaller plans, where a script refuses the transcription unless two readers agree on every number. No other toolkit agent requests Haiku. The bundled /pcv sets its own agent models: its critic requests Haiku, and its builder, research and verifier agents request Sonnet. Anthropic’s pages were read on 20 October 2026; the reasons and sources are in references/model-roles.md.

What the files cannot guarantee. They name the model each agent requests. An organization’s model allowlist, CLAUDE_CODE_SUBAGENT_MODEL_FORCE, an API key in your environment, or an alias that Anthropic moves can change what runs. Run /tasks to see the model each agent ran on (Subagents), and /model to see what your account offers.

/coa or /pace: Which One Do You Need?

Both commands spawn independent agents. The difference is the type of question you're asking.

/coa — Council of Agents/pace — Parallel Consensus
Question typeMultiple valid answers existOne correct answer exists
GoalStructured disagreement & synthesisVerified, cross-checked deliverable
OutputAdvice; you decideConsolidated result ready to use
Best forResearch design, methodology choices, strategic decisionsNumerical verification, proof checking, document drafting
Rule of thumbNo right answer? Use /coa.Right answer exists? Use /pace.

Observed: What the Commands Caught (Single Author, Not Benchmarks)

CommandWhat it preventsWhat it produces
/audit A cited figure changed silently when moved between documents. The error reached a print-ready deliverable. Only a grep against the source, at the last step, caught it. A line-by-line verification report with VERIFIED, MISMATCH, and NOT ON DISK verdicts for every cited value in the document.
/pace A logical error in an analytical calculation passed single-agent review undetected. Independent parallel agents caught it before the result was reported. The correction was material. A consolidated, cross-checked deliverable with an explicit convergence and divergence analysis showing exactly where agents agreed and where they didn’t.
/coa A methodological choice appeared settled until a council perspective surfaced the one assumption that made it fragile. That assumption became the focus of subsequent validation work. A synthesis of the separate perspectives: where they agree, where they differ, and a recommendation with the conditions that would reopen it.
/pcv By design, not a recorded catch. It prevents building the wrong thing by requiring human approval of a plan before any construction begins. Scope ambiguity and unstated assumptions are resolved at the moment of lowest cost. An approved, adversarially reviewed plan with verification criteria defined before any line is written or any file is changed.
/startup By design, not a recorded catch. It prevents losing track of where a project stands when multiple workstreams are active across sessions. It rebuilds the state from your records, not from memory. A ranked briefing from your own session records: what is done, what is blocked, and what to do next.

Methodology note. All agents in /coa and /pace are Claude models, and most roles use the same one. Agreement between them shows consistency within one model family, not independent validation. A cross-check by a model from another provider (optional, through a separate MCP integration) partly addresses this.

Common Questions

Does this work in a collaborative lab with multiple researchers?
Yes. Each researcher installs the toolkit independently in their own Claude Code environment. /commit and /startup work on your local working tree and your own summaries, so they do not touch anyone else’s work. On a shared codebase, the grouped commits from /commit make review easier.

How much has this actually been used?
Since April 2026, on a PhD project spanning simulation modeling, academic writing, formal proof verification, and conference presentations. The measured counts are above; they come from a script you can run on your own logs once the usage counter is installed (bash install.sh --hooks).

Can I use ChatGPT, Copilot or another assistant instead?
For twelve of the tools, yes (three fully, nine with limits): see Use the Tools in a Chatbot. The rest need Claude Code, because they read your files, run checks and start independent agents, which a chat cannot do.

Installation

Prerequisite: Claude Code must be installed. The toolkit runs inside Claude Code, not separately.

  1. Clone the toolkit (pinned to v2.2.0).
    git clone https://github.com/jbenhart44/Research-Toolkit.git
cd Research-Toolkit
git checkout v2.2.0
  2. Run the installer.
    bash install.sh                 # the full toolkit
bash install.sh --hooks         # also the four optional hooks (none is registered)
bash install.sh --addon-seats   # also three more /coa seats
    It installs all 24 commands and the five /coa seat agents. Upgrading? Re-run it from the new checkout. What changes in v2.2.0: skill backups go to ~/.claude/toolkit-backups/, outside ~/.claude/skills/; --hooks copies four hooks and registers none; /dailysummary, /weeklysummary and /runlog are now /daily-summary, /weekly-summary and /run-log, and for one release the old names point to the new ones. Installs older than v2.0.2 wrote no run reports, because the installer did not copy the run-report helper.
  3. Restart Claude Code, then run /setup.
    It asks about your project, folders, workstreams and which Claude account you use, and writes ~/.claude/toolkit-config.md. Upgrading from an earlier version? Run it again: it asks the account question and writes the transcription model.
  4. Type /pcv in any Claude Code session to verify it works, or /help if you are not sure where to start.

Optional Hooks

The toolkit works without these. They are for people who use Claude Code hooks; skip this section otherwise.

bash install.sh --hooks copies four hooks to ~/.claude/hooks/ and registers none: which guards run in your sessions is your decision. python3 scripts/register_hooks.py prints the settings entries for the ones you choose, to paste in yourself.

HookWhat it does
usage_counterrecords each command use; scripts/usage_counts.py reports the counts
token_budget_guardasks before an agent call once a session’s estimated tokens pass your limit
summary_folder_guardnotes a dated summary written outside your summary folders
protect_filesblocks a write to one of your protected_files; reading stays allowed

protect_files holds no list of its own: it reads what it protects from ~/.claude/toolkit-config.md, and with nothing there it allows everything.
